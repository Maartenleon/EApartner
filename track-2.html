Track 2

Architecture
as a Function

The EA function is not a role — it is a set of capabilities. Each can be assessed, prioritised, and deliberately improved. This is how you build an architecture function that compounds in value over time.

Sound familiar?

Architecture keeps slowing delivery down — why does this keep happening?

Architecture becomes a bottleneck when it shows up as a late checkpoint. The fix is an engagement model where architects are embedded early — so governance adds clarity to delivery rather than friction at the end.

We have architects, but nobody consults them. Their work doesn't land.

Architecture loses relevance when it isn't present where decisions are made. I assess your engagement model and help you redesign it — so teams pull architecture in because it makes their work better, not because they're required to.

How do we actually measure whether our architecture function delivers value?

Value from architecture is measurable: fewer rework cycles, better investment decisions, faster onboarding of new initiatives. I connect your maturity assessment to concrete outcomes, so improvement has a cost — and a return.

Architecture decisions keep getting made without us — how do we change that?

Architects get bypassed when they show up too late or when their process feels like overhead. I redesign the engagement model so architecture is present in the decisions that matter — with a light enough touch that teams want it there.

The model

Six capabilities,
one coherent function

An architecture function delivers value through six distinct capabilities — each independently assessable on a five-level maturity scale and independently improvable.

Six capabilities

improve

Each capability is independently improvable. Maturity is a direction, not a destination — every step is a deliberate choice about where the function needs to go next.

01

Direction

The mandate, vision, and principles that give the EA function its own north star — a defined scope, architecture vision aligned to business strategy, and principles that set real boundaries on design decisions.

02

Governance

Decision rights, review triggers, and the accountability that keeps architecture authoritative. Architecture Decision Records with rationale — governance that adds clarity rather than process.

03

Landscape

Visibility of the current and target state across all architecture layers — maintained as a living asset with domain ownership, versioning, and a dependency map that sequences and de-risks change.

04

Standards

Reusable decisions that prevent reinvention. Technology standards vetted with rationale, patterns for common architectural problems, and an exception process that feeds learning back into the library.

05

Engagement

How the architecture function stays connected to the work — present in initiatives early, useful in real time, never just a checkpoint. A clear support model for who gets involvement, and when.

06

Portfolio

Architecture connected to investment decisions. Technical debt quantified and tracked, investment sequencing based on architecture dependencies — where the function becomes accountable for the return on technology spend.
